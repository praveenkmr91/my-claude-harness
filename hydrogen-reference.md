Deeper sections of `~/.claude/hydrogen.md`, loaded only when a session touches the domain. Injected once per session per domain by `~/.claude/hooks/hydrogen-context.sh`; Read the section directly when reasoning about a domain without a matching tool call. ## Ejection — an ownership tax, size it right
- Ejecting inherits security patches, upstream drift, and merge pain. One-file change → **fork that file in-place** as owned code where a seam lets our code substitute it (`dataSource`, our own import); eject only for genuinely multi-file/deep customization. A file inside a transitive package with no such seam → eject it, never `patch-package`.
- Flow: `npm run eject:hydrogen <pkg>` (or repo-local `scripts/eject-script.js`) → `custom/<pkg>` wired as a `file:` dep. That dep may be a **symlink** (npm workspaces) or a **real copy** (bun) — verify which before assuming dedupe/override mechanics apply (npm `overrides` can't reach transitives through a symlinked package).
  - Pass `<pkg>@<installed version>` when latest differs or consumers pin exactly: unversioned installs latest, whose deps may bump `core.*` majors (nested singletons) and whose link no longer satisfies exact pins (each consumer keeps a nested unpatched copy). A version argument makes the script append `-x.y.z` to the folder — rename it off (`mv`, `file:` path, `npm install`) before commit 1.
- **Two commits, always:** (1) raw ejected files, unmodified, committed before any edit to the package; (2) customization on top. Keeps the fork delta reviewable and upstream reconciliation tractable.
- Ejected widgets often keep a vestigial `@additiv-hydrogen/envs.*-env` (Bit) devDependency dragging the whole `@teambit/*` toolchain into install (thousands of packages). Once the host Vite build owns `custom/`, strip it and regenerate the lockfile.
- **Nested singleton state (prod-only bug class).** Ejection can leave nested copies of stateful `core.*` singletons (`core.di`, `core.event-bus`, `core.i18n`, `ui.configs`) in the ejected package's own `node_modules` — each holds independent module-level state → split-state bugs: a subscriber never receiving events, a widget reading an unbound translate container and rendering raw `{{key}}`. Surfaces in **production/Rollup only** — `vite dev` pre-bundles the scope to one instance, so a clean dev session does not prove absence.
  - Fix: add the package(s) to `resolve.dedupe` in `vite.config.ts` (verify dist parity first — byte-identical dist = safe to collapse).
  - Dedupe **surgically**: a binder package that calls `container.bind(id)` on init must be deduped *alongside* the container it binds into, or the collapsed container gets multiple bindings for one identifier → inversify "ambiguous match" crash. Map what `.bind()`s into a container before deduping it.

## Layouts & widget boundaries — structure has a convention too
- **A list and its detail screen are SEPARATE widget packages, with ZERO edges between the two halves.** This is a pair rule, not a global one — widgets compose other widgets freely (hundreds of widget→widget imports in source: `custodian-onboarding` → `modify-investment`, `proposal-overview` → `new-interaction`, …). Four pairs upstream (`activity`, `announcements`, `conversations`, `instruments`); `instrument-details` imports only `data.*`/`contracts.*`/`core.*`/`ui.*`, never the list widget. **Corollary (the point): a list/detail split that looks impossible because the halves depend on each other means the shared code is in the WRONG LAYER — inside a widget instead of `data.*`/`contracts.*`.** Move it out and the cycle disappears; never conclude "can't split".
- **`StepContent` (`ui.layouts.step-layout`) IS the card, and owns its own footer** via `actions`, plus `isErrorActions` + `errorActionsMessage` (renders an `ErrorBox` ABOVE the actions bar) and `stickyActions`. Do not pair it with `ContentBoxFunctionBar` — that one is `ContentBox`'s half. Picking the wrong pair is how a submit error ends up rendering *below* the action bar.
- **`StepContent` has no `title`/`options`.** Compose the header from `Title` + `Separator` — see `widgets/wealth/modify-investment/components/modify-step-layout.tsx`, the canonical example (Exit/Back left, primary right via `ms-auto`). `StepContentFooterBar`'s `headerComponent` is a raw node, so it gives nothing back. Header-outside-the-card is also idiomatic: `ProcessContent` takes `header` above its card.
- **Widget error state: pick the primitive by whether the widget has a `ContentBoxContent`, and NEVER pass `errorBoxClassName`.**
  - `ErrorBox`'s signature is `className = 'text-sm text-danger-700'` — a **default parameter** — and it renders `classNames('gap-2 bg-danger-200 rounded-md flex flex-col p-6 text-center font-medium', …, className)`.
  - So any class you hand it (directly, or via `ContentBoxError`'s `errorBoxClassName`) silently DROPS `text-sm text-danger-700`: the message renders at inherited size in near-black on the pink ground.
  - The padding you passed also collides with the base `p-6` rather than overriding it, because that call is `classNames` (filter+join), not `twMerge`.
  - Two correct shapes, both with a bare `ErrorBox`:
  - (a) a list/accordion widget that renders straight into `ContentBox` → `<ContentBoxError isError errorMessage={t('common.something-wrong')}>` wrapping the content, full-bleed, which is fine because the content is full-bleed too (`widgets/wealth/maturing-bonds` summary, `widgets.wealth.compliance-breach`);
  - (b) a **table** widget whose table is edge-to-edge inside `<ContentBoxContent className="!p-0">` → branch the wrapper, `isError ? <ContentBoxContent><ErrorBox>…</ErrorBox></ContentBoxContent> : <ContentBoxContent className="!p-0">…table…</ContentBoxContent>`, so the error picks up the standard `p-4 sm:px-6` while the table keeps its own cell padding (`widgets.wealth.funds-list` is the exemplar).
  - Getting this backwards renders the error card flush to the card edges with no inset, which reads as broken — `ContentBox` wraps children in a plain `<div className="h-full">` with NO padding, so `ContentBoxContent` is the ONLY source of that inset, and `ContentBoxError` cannot be inset without the class that breaks its text styling.
- **Never nest `ProcessContent` inside `Content`.** `process-content.tsx` emits `<main id={MainContentId}>` unconditionally and `ui.layouts.base`'s `Content` defaults `as='main'` with the same id (`Content.tsx:22,28`). A `Workflow`-hosting route must therefore NOT wrap in `Content`.
- No upstream precedent for "StepContent as a detail page with a real footer bar" — every monorepo consumer is a wizard step except `proposal-overview`, which strips the bar via `actionsClassName`. Fine to do; don't hunt for an exemplar.
- **NO controlled accordion exists — forcing a panel open means remounting it.** A sweep of every prop of all 288 packages in the component map (not a name grep) finds only `ui.components.accordion-section` takes `open`, and its controlled mode is a trap — `DisclosurePanelWrapper` honours `open` (bypassing `Disclosure.Panel`), but `Disclosure.Button` still derives `aria-expanded` from Headless UI's *internal* state, so a programmatic open renders a visible panel announcing itself collapsed. `accordion-single` has `defaultOpen` only, and monorepo source == installed dist for both, so no bump unlocks this. Consequence: `defaultOpen` + a remount key is the CORRECT pattern for "reveal this card on a blocked submit", not a hack to refactor away — and any CSS keyed on `[aria-expanded=true]` (the only handle `AccordionSingle` gives you, since it exposes no open-state callback) breaks under `AccordionSection`.

## Workflows
- **`ProtectRoutes` DOES block a browser Back — and a router holds exactly ONE blocker.** Pressing Back inside a guarded wizard restores the URL and raises the confirm modal, because react-router 7.12 calls `shouldBlockNavigation({historyAction})` on the POP path too (`chunk-EPOLDU6W.mjs:1484`) and reverses with `history.go(-delta)`.
  - Never hand-roll a `pushState`/`popstate` trap for this.
  - The one-blocker part is the trap: `shouldBlockNavigation` takes the LAST entry of `blockerFunctions` and only `warning()`s on more than one, so a second `useBlocker` deeper in the tree silently DISPLACES `ProtectRoutes`' instead of adding to it.
  - To block on a deep condition, lift the condition to the route that owns `ProtectRoutes` (a context whose setter the route passes down) and widen its `shouldBlock` — `useBlocker` re-registers per render (`blockerFunction = useCallback(…, [basename, shouldBlock])`), so an inline `shouldBlock` arrow always closes over fresh state.
  - Keep any `state.forceNavigate` escape hatch checked FIRST, or a stuck condition traps the user with no exit.
- **A workflow's milestone set is per-workflow, NOT a fixed pipeline, and the milestones are independent of one another.** Some workflows take a `populate-data` update after `/start`; others carry their whole payload in `/start` and never take one. `retry` is its own milestone, unrelated to `populate-data` — a workflow can have retry without populate-data, and neither implies the other. "Start must be followed by an update" is therefore false in general: check the actual workflow before assuming a step exists or is missing. Oracle = `GET /v1.0/workflows/{name}/schema` for the payload-carrying milestones, plus a grep of the app's own `updateWorkflowApi`/`useWorkflowUpdate` call sites for the rest (retry sends an empty payload, so the schema does not list it — see the update-envelope note). Worked instances live in the consuming project's memory, not here.
- **Corollary: the status read after `/start` is not redundant filler before an update.** `/start` answers 200 the moment the engine ACCEPTS the request, not when the saga succeeds — a synchronous validation failure still returns 200 with a running `state`, and only the status read reports `…Failed`. Seed the outcome from `/start`'s `state` if you like, but do not drop the read.
- **A status response carries `isCancelable` and an `errors[]` array; both are load-bearing.** Cancelling a run the engine marks `isCancelable: false` answers **500** ("The workflow is not cancelable"), so gate any Terminate affordance on that flag. `errors[]` is the ONLY channel for a saga failure reason — the call answered 200, so no axios error carries it — and the engine wraps the originating service's rejection in prose plus its serialized body (`… failed. Error: {"code":"ValidationFailed",…,"ValidationErrors":[{…}]}`), so dig for the innermost message and fall back to the whole string.
- **Workflow verbs bind the workflow-name at hook-init from a fixed const — NO prop/context injects a custom name.** Reusing base workflow UI (containers, headers, step schemas) under a custom name 404s at every unforked seam (status/read/write/cancel/subscribe), and the error surfaces on some other screen, not at the reuse point. Fork all seams, not just the leaf data hook.
- **`Workflow`'s `dataSource` prop is FROZEN at first render — never use it for live page state.** Two independent mechanisms (installed 8.x): its `React.memo` comparator checks only `isReadonly`/`parentLinkPattern`/`homePageLink`/`totalSteps`/`workflowContext`, so a changed `dataSource` does not even re-render `Workflow`; and `workFlow = useMemo(() => generateFlow({…}), [totalSteps, homePageLink, parentLinkPattern, data, currentSchema])` omits `dataSource`, so the value each step receives is captured once. (`data`/`currentSchema` are themselves `useMemo(…, [])`.) The only live channel into steps is `workflowContext` — memo-compared by reference, so `useMemo` it. Otherwise follow the upstream pattern: **steps call their own hooks** (custodian-onboarding's steps do), which react-query dedupes.
- **`Workflow` does NOT mandate a `:processId` route param.** `useProcessStateId` reads `useParams().processId` *by that exact name* then falls back to an event-bus value (`data/wealth/app/use-process-state-id/use-process-state-id.ts:12,26`), and `WorkflowProps` never mentions it — `:processId` is just modify-investment's route convention. A route keyed `:id` yields `undefined`, not a collision.
- **`Workflow` routes each step, so crossing a step boundary UNMOUNTS the step component.** Any in-flight form state must round-trip through process-state (`useProcessStateStep(name).save`) or live above `Workflow`. For a plain confirm-before-submit step, a search param on the same route keeps one mounted form and serializes nothing — cheaper and safer than a routed step when the payload is money.
- **`useWorkflowsStatus`/create/update/cancel omit `workflowName` from the react-query cache key** (only `processStateId` + the `queryKey` option) — a custom-named status hook MUST pass a distinct `queryKey` or it collides with the base hook on the same id.
- **Process-state READ hooks are hardwired to the route's id (`useProcessStateId`); only `save` takes a per-call id override.** Saving under one id while the route holds another silently desyncs until refetch.
- **Inline `workflowContext={{…}}` fails `Workflow`'s memo on every parent render** (by-reference compare, per the `dataSource` bullet) → the whole workflow subtree re-renders with the page; `useMemo` it. Gotcha that makes the `useMemo` decorative: a dep list containing a **hook return object** (fresh literal every render) recomputes every time — stabilise those returns or accept the re-render knowingly.
- **A `Workflow` re-render does NOT remount the step** (installed dist; don't re-add the opposite claim). `createRoutes` *is* unmemoized, but the element *type* (`route.Component`) comes from the **memoized** `workFlow`, so React reconciles: steps re-render, form/accordion state survives. Refetch loops need another explanation — see the `cacheTime:0` latch trap in *Data & caching*. Crossing a step boundary still genuinely unmounts (bullet above); re-rendering at one route does not.
- **`custodian-onboarding` = the mature workflow exemplar** — copy its container nesting (`SkeletonWrapper→WorkflowErrorBoundary→WorkflowCompleteBox→Workflow`) and status→UI handling (status query `onSuccess` + SignalR subscription feed a `StatusState`; dynamic per-product schema selection; resume = overview links gated on `data[step].status === 'completed'`, not a stored pointer). `prospect-onboarding` shares only the container nesting — thin static 2-step, no readonly/terminated logic. Credit/request-details flows are WIP. Don't pattern off either.

## Data & caching — hooks that look configurable but aren't
Some Hydrogen data hooks accept a prop (`idProp`, a `where` filter) but silently ignore it in favour of a route-bound id (`useXxxId()`) or a hardcoded page size. Before treating such a hook as a drop-in for a differently-keyed query, verify which value actually wins. Two symptoms:
- A cache key that omits the differentiator you think it depends on → cross-consumer collisions or missed refetches.
- A paginated list-hook (default e.g. `take: 10`) used to resolve ONE saved id against its options → an id outside page 1 silently resolves blank. Anchor with an explicit `{ id: { eq: value } }` filter when resolving a specific saved id.
- Hooks with internal `keepPreviousData` (`useSecurityResearchData`, `usePortfoliosData`) hold the *previous* key's rows on a key switch with `isLoading` false — gate loading UI on `isFetching`. A wrapper hook should expose one flag `isLoading: base.isLoading || base.isFetching` so consumers can't pick the wrong one.
- **Never gate a mount on a `cacheTime:0` query that 404s dataless** — its `status` reverts to `'loading'` on every refetch with `isSuccess` and `isError` both false, so `isSuccess||isError` never latches; if the gated child re-observes the same key, mount ↔ unmount ↔ refetch loops forever. Latch the decision once in `useState`. Static dist-reading misdiagnoses these loops — reach for runtime instrumentation (mount/unmount + gate-value logging in the browser) early.

## Theming — `@additiv-hydrogen/ui.theme`
- **`getColor(token)` fails silently on an unknown token** (`ui/theme/utils.ts`, same in `ui.theme@1.0.2`). It reads `--colors-<token>` from `:root`; a missing variable yields `rgba(undefined,…)` and a non-triplet value `rgba(NaN,…)`. Both are invalid colours, so an SVG `fill` or CSS colour paints **black**, and neither tsc nor lint notices. Before using a token, confirm the app's theme schema defines it, or copy the tokens a sibling already uses.

## Tables — `@additiv-hydrogen/ui.components.table` (`useTableControl` + `<Table>`)
- **ONE `FieldsType[]` drives columns AND the filter — never split them.** Feed the same array to `createTableState({ columns })` and `<TableFilter fields={} >`. `createTableState` renders each header from `label || title` (FieldsType has `label`, no `title`) and honors `isVisible`; `TableFilter` picks the `isFilterable` fields (missing = excluded — just mark `isFilterable:true`+`filters` on the ones you want). **Read `widgets/wealth/instruments-list/fields.ts` before writing any table's fields.** Static local fields → set `label` explicitly; `translateFields`/`useTableLazyFields` is only for lazily-loaded remote fields.
- **Pass RAW rows; never pre-transform.** `createTableState({ data })` spreads items untouched; `getRenderCell` resolves each column by `getByPath(item, key)` (dotted keys work), then formats via the column's `fieldType` (`FieldTypes[fieldType]` — `Date`/`DateTime`/`Decimal`/`Percentage`/… scale+localize; `Percentage`=fraction×100; null→`Empty()`; loading→skeleton, all handled by `getRenderCell`). A `buildRows`-style pre-map is redundant. **Set `fieldType` for plain formatted columns** — `getRenderCell` runs inside `TableBodyItem`'s render (a real fiber), so even hook-using renderers (`renderPercentageCell`→`useTranslate`) work. Reserve `customCells[key]` (`({item},isLoading)=>JSX`, reads raw item) for composite/interactive columns — and a custom cell renders *before* the skeleton guard, so it must handle its own `isLoading`.
- **`customCells` CAN call hooks directly — every desktop cell has its own fiber** (installed dist; don't re-add the opposite claim).
  - `TableBodyItemContent` is a real component rendered via `createElement`, and `renderCell` → `customCells[key](data, isLoading)` executes inside its render.
  - **Mobile differs:** `MobileItem` calls `slot(1)…slot(8)` in its OWN render body, so all mobile cells' hooks share ONE fiber and its `if (!column) return null` guard means the hook count shifts when a column's `mobileOrder` changes — keep mobile cells hook-free or delegate them to a named component.
  - Delegating a desktop cell to a named component (`amount: ({item}, l) => <MoneyCell item={item} isLoadingCell={l}/>`) is still the better default when the cell needs its own data: it isolates the subscription and re-renders.
  - And prefer lifting a value the WHOLE table needs (or that client-side sort must read off the row) into the data hook — a per-cell hook multiplies subscriptions by row count and cannot feed `sortPositions`-style raw-property sorting.
  - Loading (the custom cell owns it): `renderStringCell(value, isLoading)` (+ `renderDecimal/Number/Date/DateTime/Percentage/EmptyCell` siblings, all `SkeletonWrapper`-based) from the table pkg for string cells — keep your guarded formatters and pass the string in; `SkeletonWrapper` (from `ui.components.skeleton`, NOT the table pkg) for JSX cells.
  - `SkeletonLine` defaults to full width — don't pass an explicit `Skeleton` except for a non-default shape.
  - Type the map `CustomCellTypeWithLoading<Row>`.
- **Seed a default filter chip as the `useState` INITIAL value — never via a mount-effect `setFilters`.** `useTableFilter` captures the `filters` prop ONCE at mount then diverges, and its unmemoized `initCondition` resets internal state whenever it goes empty → an effect-seeded default self-clobbers (chip vanishes, `{and:[]}` on the wire). `useTableControl` has NO initial-filters param — a table using neither sort nor saved-filters: drop it, own `filters`/`page` in local state, replicate `onChangeFilter` = `setPage(1); setFilters(next)`. Seed's `option` must be a key from the field's `getOperationsOptions`; `createFilters` expands multi-value `in` to `{or:[…]}` — equivalent, backend-accepted. Never inject the default inside the data hook (invisible + not editable).
- **Pass `onSort` RAW.** Hook's `onSort` is single-arg `(e)=>setSorting(e)`; `<Table onSort>` is `(clickedKey, mergedNext)`. `onSort={onSort}` binds arg1 → single-column replace (universal idiom). A wrapper forwarding arg2 (the merge) flips it to accumulate — old columns never clear.
- **`footerData` is a real `<tfoot>` but its styling is a trap (runtime-verified, not readable from types).**
  - `TableFooter` renders through the same `TableBodyItem`/`renderCell` path (so `fieldType`, custom cells, the null→`Empty()` rule all behave), but:
  - (1) it hardcodes `rowClassName="bg-neutral-100 rounded-b-md"` while `TableBodyItem`'s own `<tr>` carries `bg-white` and merges via `classNames` (NOT twMerge) — `bg-white` wins, the footer renders WHITE;
  - (2) that same `<tr>` carries `[&:last-of-type>td]:border-none`, which nulls the `border-t` in `cellClasses.footer`;
  - (3) footer cells get `cellClasses.footer` (`py-2`, weight inherited ~400) and **`bodyCellClassName` never reaches them**, so a totals row renders LIGHTER than the body rows it sums.
  - What does work: the `<table>`'s own `divide-y divide-neutral-200` puts a 1px rule between `tbody` and `tfoot`, so the separator is there.
  - Emphasis has to come from inside `renderCell` — branch on the row (`item.id === 'total' ? 'font-bold' : undefined`) and style the returned span; there is no per-footer-row class hook.
  - Don't reach for `columns[].params` to patch it: `TableBodyItem` spreads `...params` AFTER `className`, so a `params.className` replaces the computed cell classes outright.
- **Sort doesn't reset page; `onChangeFilter` does.** No monorepo table resets page on sort (`totalCount` unchanged). Leave page alone on sort; reset only on result-set-changing controls (a period/`where` `<Select>` → `setPage(1)` in the same handler, else overshoot triggers a cursor-guard second refetch).

## Forms — `@additiv-hydrogen/ui.forms.hydrogen-forms`
- `Button` defaults to `type="button"`; pass `isSubmit` for submit — a `form` attribute alone won't wire it.
- `formRef.current` is DOM-patched via `useEffect` (`trigger`/`reset`/`setValue`/… attach after mount), so anything read off it on the initial render is stale/absent under `validationMode: 'onChange'` — including a hand-added `isValid` (the package never exposes one; that's a consumer-widget addition). Gate submission through `handleSubmit`, not a raw ref read.
- Built-in field wrappers (`select`/`textfield`/`checkbox`) call `triggerValidation` internally on change; a **custom `type: 'render'` field** does NOT — call `trigger(name)` yourself in its `onChange`.
- **Per-field async option source** for a `select`/`multi-select` (instead of the global `useSchemasListsSearchKey` DI default hitting `/schemas/lists/search`): set `component.props.listKeyDataSource` alongside `listKey` + `valueKeyBy: 'id'`. The datasource is a hook `(listKey) => { data: {id,label}[], isLoading }`; the spinner gates on a truthy `listKey`, so set it even if the datasource ignores it.
- `render` does NOT work on `type: 'select'` — it's its own component type; on a select it's silently ignored and the field falls through to the container-datasource path (symptom: unexpected `/schemas/lists/search` calls, 422s on unknown list keys).
- The `data: OptionType[]` prop path is for cascading/derived options computed by the parent (loading hardwired `false`, synchronous) — use `listKeyDataSource` for an independent self-fetching async list.
- **`HydrogenFormsContext` cannot host a form ARRAY (installed 8.0.0).**
  - It looks like the sanctioned BYO-`useForm` seam (and `FormContextWrapper` genuinely is just `<FormProvider {...formMethods}>`, a one-line file — adopting it over a raw `FormProvider` is a rename, not a gain).
  - Three closed doors:
  - (1) `nameForm` is declared on the props but **never forwarded** to `FormComponents` in the context variant (only `HydrogenForms`' `multiple` branch forwards it), so descriptor keys must be fully qualified (`splits.0.bankId`);
  - (2) `fieldComponents = useMemo(() => parseComponents(components), [readonly])` then **freezes** those keys — a `useFieldArray` middle-`remove()` leaves the survivor mounted at index 1 still writing/reading `splits.2` (blank inputs + errors that never match = silent loss);
  - (3) the `gridIndex` escape (`ui/forms/panel-list/component/grid-table-columns.tsx`) is unusable outside table cells — it strips every field label, breaks `getValue` on `0`/cleared cell values, and its `handleChange` mutates in place and returns before `onChange`, bypassing `useFieldArray`.
  - Own the RHF↔wrapper bridge instead.
- **Error-label translation IS reusable logic, but only on fully-qualified keys.** `generateErrorLabel` lives *inside* the `FormComponents` body (closes over `t`/`getValues`), so it is unreachable — but its semantics are `get(errors, component.key)` (a real deep-path reduce, so `{splits:{'0':{...}}}` plain-object shapes resolve identically to arrays) then `t(msg, { inputName: t(label), ...values })`. Reimplementing that in a custom bridge is ~12 lines and correct; skipping it renders raw i18n keys.
- **`TextfieldWrap` wires `isRequired` to two unrelated behaviours, and you cannot satisfy both.** `LabelTooltip` renders the "(optional)" suffix only on `isRequired === false` *strictly*, while the wrapper derives `nullable` from `isRequired !== undefined` (`textfield-wrap.tsx:182`). Pass a boolean → optional fields get labelled but `nullable` leaks onto a `<textarea>` as an unknown DOM attribute; pass `undefined` → no leak, no "(optional)" anywhere. Keep the boolean: the warning is dev-only, the label is not.
- **`TextfieldWrap` spreads its whole `formFieldProps` onto the rendered input**, including its own `addonLeading`/`addonTrailing`/`iconTrailingElement`/`withRegionValidation`/`prefixElement`. On the `textarea` path those are unknown DOM attributes → a fistful of React warnings no consumer can suppress (stock `HydrogenForms` produces them too). Don't chase them from the consumer side; fork the wrapper or accept them.
- **`DecimalInput` (`ui.components.text-input`) coerces a cleared field to `floatValue: 0` unless BOTH `nullable` AND `allowEmpty` are set** — either alone still yields 0, via two independent mechanisms: keystroke path (`getFloatValue(null)` → 0 when not nullable) and a value-prop pushback effect that re-poisons a stored null with 0 (`disableDecimalInputSync` does NOT stop it). In trade/allocation forms 0 is a real submittable value, so clear→0 silently queues a live trade with Save enabled. Browser-verify the cleared state — invisible to tsc/lint.
