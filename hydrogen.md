## Reuse hierarchy — stop at the first fit
Hydrogen instantiation of the global dependency ladder (global CLAUDE.md) — edits to either must keep them aligned.
1. Hydrogen hook/component/type as-is.
2. A Hydrogen primitive composed (e.g. a layout built from existing primitives).
3. In-place fork of one Hydrogen file with a minor edit (**not** a full package eject).
4. An OSS library — only if Hydrogen genuinely can't deliver it.
5. Custom from scratch — last resort, needs explicit justification against the above.

Prefer the Hydrogen wrapper over the raw lib even when that lib is a direct dep — the wrapper carries locale wiring and project conventions the raw call loses: `formatLocaleDate`/`convertToISOString`/`toUTCFormat` over `date-fns format`, `PreciseCalc` over raw arithmetic, `formatNumberCurrencyDisplay` or an i18n currency template (`t('{{val, currency(USD)}}', { val })`) over `Intl.NumberFormat`, `truncateDecimalNumber` over `toFixed`. **Exception:** pure date arithmetic with no locale/formatting concern (`addMonths`, `isBefore`) — direct date-fns is fine when no wrapper exists. When porting from a non-Hydrogen reference, translate each raw call (`Intl.*`, `toFixed`, `toISOString().slice()`) to its Hydrogen equivalent during the port; never copy line-for-line. (A PostToolUse hook, `hydrogen-util-guard.sh`, flags these signatures on every write in Hydrogen repos.)

## Source-vs-installed — the verification discipline
- The source monorepo is frequently **ahead** of an app's pinned version — a symbol in source may not be importable today. Confirm it in the installed `dist/`; `tsc --noEmit` is the final arbiter.
- `tsc` clean + `vite build` clean do **not** prove a lazily-loaded area renders — neither evaluates lazy chunks. A package with no `exports` map can have a `/subpath` import that type-checks (against a `.d.ts` dir) yet crashes at runtime in Vite ("does not provide an export named 'default'"). Import from the main entry unless an `exports` map documents the subpath. **Browser-verify newly wired areas** — don't trust the static-analysis gate alone.

## i18n — backend-driven, not local CSV
- Translations are fetched at runtime from a **backend resourceset API** (`/resourcesets/{name}/?language={lng}`) via `core.i18n`'s `InitLanguage` — the local CSV is only the source that must be synced/uploaded to that backend per environment.
- So new keys render as the raw key string (`common.skip-to-content`) in any environment whose backend resourceset isn't updated yet — **expected, not a frontend bug**. Verify the JSX composition is right and move on, don't chase it.
