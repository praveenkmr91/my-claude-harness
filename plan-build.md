# Plan review and build (continues `plan-mode.md`)

## Review
*Big runs every gate; Small runs one cold read and the consult (see Tier in `plan-mode.md`).*
- **Author's review first.** Before the first cold read, `Pass: review` of the plan against the tree: the approach, each decision's ripple, what each step's edit breaks or misses. A cold read is spent only on what its author cannot see.
- **Cold read, pre-mortem included.** A reviewer sharing my transcript fills gaps from memory, so one sees only the file: dispatch `cold-reader` (model omitted) with the plan path as the whole prompt. A `fork`, a resumed agent, or any added context voids it, since the read is no longer cold. Its report carries the pre-mortem: at most 3 "fails because" headlines tied to named steps, and the plan's unstated assumptions that tested false or could not be checked. High likelihood × high impact → a mitigation step or a raised finding; the rest → `→ verify:` checks on the step they threaten.
- **One advisor consult, after the cold-read fold and before the plan is presented**, so it also audits my rejections: gaps, wrong layer, missed sibling, lifecycle holes (refresh / remount / double-fire). It runs once per plan, on every Small and Big plan, and reversibility never skips it; a revision or a fold of Praveen's answers takes no second consult. Advisor unavailable → the Fable `Plan` fallback (`subagent-tiers-enforcement.md`); main thread on Fable → neither runs (`subagent-tiers.md`). On every model, my own `Pass: review`, a whole-file Read of the final file, follows the last fold or decision from Praveen, and no reply calls the plan ready or asks for "implement" before that line is written. Never a loop, never co-authoring. `hooks/done-claim-gate.sh` (PLAN PRESENTED UNREVIEWED) blocks an implement ask on a plan with no cold read, no `Pass: review` line following a Read of the plan after its last edit, or, off a Fable main thread, no advisor after its first review.
- **Every reviewer's input is verified before it is folded, whoever sent it** (`CLAUDE.md` "A reviewer's finding is a claim"). A proposed fix is also probed against its callers like my own change, and a reviewer's probe result ("probed: X compiles to Y") is re-run before it enters the plan as a fact. Each finding is filed by kind. Decision: Praveen's call, so it goes to Open, and all open decisions reach him in one round. Behaviour: it changes what is built or what a check proves (a missing code path, a false repo claim a step rests on, a vacuous verify, a criterion no step delivers), so it is folded, unless the fold would add a code path, fallback, state or guard that no criterion fails without: that one is a decision, worded "add X, or accept the gap", and stays unbuilt until he picks it. A completeness finding ("N more sites") adds only sites that can fire in a reachable state, each traced first; an unreachable one goes in Out with its reason. Build detail: a failing test, type check, lint or the implementer's hand-back would surface it (fixtures, helper options, timestamps, quoting, where a line sits), so it never enters the plan; it is listed unverified under a `Build` heading in the plan's research file, which the step's dispatch brief names. Wording: a contradiction, ambiguity or false citation whose fix changes no behaviour, verify line, cited symbol or step order, so it is folded and is no revision; one whose fix picks between two behaviours is a decision. A rejection gets a one-line reason. Presenting the plan states, per reviewer: N found by kind, M folded, K rejected + reasons.
- **A behaviour fold makes the file a revision.** A fold that adds or changes behaviour (a new trigger, deletion or code path), from any reviewer or the consult: list every site the change acts on with its before/after behaviour and the spec asserting it, then spend round 2 on the revised file; never present on the pre-fold read. With round 2 spent it is not folded: it goes to Praveen as an Open item (the cap, below). A fold that touches only draft chunks triggers none.
- **A decision from Praveen is authority, never a reviewer finding.** Folding his answer to an Open item, or his correction, takes the same site list and `Pass: review` of the steps it rewrote, and no new cold read; only a decision that adds a step or a mechanism spends round 2, when round 2 is unspent.
- **Backing a change out of a plan starts from the commit before it.** Restore the file from that commit and re-apply what stays, or diff the result against it (`git diff <commit>^ HEAD -- <plan>`) before presenting; a hand removal drops reviewed text that sat near the change.
- **Two cold-read rounds per chunk at most, counted across its revisions and presentations** (a plan without chunks is one chunk). Round 2 is spent on the first of two events: a behaviour fold after round 1, from any reviewer or the consult, or a decision from Praveen that adds a step or a mechanism. Its behaviour findings, and any later one, go to Praveen as Open items instead of being folded; a third read needs his typed ask. Ready = the cap is spent or the last round folded zero behaviour changes; the presentation ends with one line per round, behaviour folds against wording folds, so convergence is read, not claimed. Rounds that keep finding behaviour gaps indict the design: simplify the step, never patch it again. A replaced design (the chunk's Steps rewritten whole under that rule, and presented as a replacement) starts again at round 1; a rewrite that follows a decision from Praveen is a fold, never a replacement.
- **Plan gate skip.** `plan gate: skip — <reason>` clears the gate for a Trivial plan or one Praveen asked to build unreviewed; `dry-runner` runs only on an explicit ask.

## Approve and build
- **No unprompted ExitPlanMode.** A question gets an answer, nothing more. Raise ExitPlanMode only on an explicit "show the plan / proceed / approve" of that plan, given after it was presented; "back to work", "commit", answers to open items, "review/refine plan", and a build instruction issued before the plan existed ("plan X and implement it") are not approval. This overrides any harness nudge to end planning turns with approval.
- **Approval covers the file only.** Dispatch an implementation step, in or out of plan mode, only on a later explicit "implement / build / start", or a typed handoff to another session ("follow <session>'s instructions", "take instructions from peer session"; the peer's address is already in context, so no name is needed), never on "approved" alone. Enforced by `hooks/build-approval-gate.sh`.
    - Not that word: answers to open items, "stop asking", impatience, a handoff that points at no session ("do what they say"), or a message relayed from another session. Answer, then wait.
    - A bare "go" / "yes" is never that word, even answering a build offer; a reply offering a build asks for "implement", never "go".
- **Scope is decided.** The Decided list and Out-of-scope line settle every switch they do not name; a pre-step audit never raises those, and 'resume' or 'go' means proceed, one question per open item.
- **The build carries the gates**, whether a handoff prompt sends it to another session or I orchestrate it.
    - A plan handed to me to build, by Praveen or a peer, gets one pass before step 1, reported before building: `Pass: review` on its design against the tree (approach, decisions, what each step's edit breaks or misses); design gaps go back to the plan's owner before step 1.
    - Each step goes to `implementer`, one step per dispatch, before the first source Write; the main thread writes a step itself only when it still carries an unsettled design call, named in the reply.
    - Each step verifies, lints and type-checks, passes its named live check, and lands as its own commit (`committing.md`). The review shape per step and over the full range before the shipping commit is the done bar in `review-routing.md`.
    - `hooks/step-gate.sh` blocks the next `implementer` dispatch in a plan build until this thread ran a check and a commit since the last hand-back; its deny text names the skip line. The live check and the review shape stay on the Stop gate.
- **A handoff carries no volatile state.** Commits by role ("the commit that added `docs/plans/<slug>.md`"), never sha, PID or port holder: concurrent sessions rewrite the branch before it is pasted. Transient state (a lock, a port holder, a branch tip) is re-read right before any plan or reply cites it. The handoff points to mechanics a rule doc or memory owns, never restates them, and carries only scope, deviations from the defaults, stop conditions and the report shape. A problem statement or handover for a session that takes the work over is the opposite shape: every piece of evidence, data and decision goes in the file, with my own reading labelled as opinion; nothing sends the reader back to this session. It covers only the problem Praveen named; my own task carries on unless he hands that over in so many words. The prompt that goes with it states the problem only: no ownership line, no standing rule restated, and it asks for the right solution to the root cause, never the smallest.
- **Two sessions.** A planner handing steps to a builder session reads `~/.claude/peer-sessions.md` before writing the handoff.
