# Committing

## When to commit
- **Commit locally at verified checkpoints, unasked.** A checkpoint is work Praveen asked for that has passed `review-routing.md`'s done bar and a `code-craft.md` read of the diff; passing lint, tsc and lenses does not prove the diff reads like a human wrote it. The Stop gate checks lint and lenses on any committing turn.
- **Not a checkpoint:** a review, recheck or question turn on anyone else's work. It changes nothing, including staging or committing a file Praveen placed; a missing step found there goes in the reply as an offer. A bare mid-turn "approved" answers the open permission prompt, never a commit.
- **Own unpushed work is mine to fix and fold, review turns included.** Confirmed findings on it: fix, re-verify, fold into its commit (Squash, below), report findings and fixes together — never a "yes to which?" list. Ask first only for an architectural or irreversible change (`CLAUDE.md` gate; a helper in an existing layer or a new i18n key is neither) or a fix that reverses a decision Praveen stated. "Own" includes work a subagent or peer session built under my supervision: an approval gate I set in a handoff is mine to clear, never relayed to Praveen. It also includes a teammate's branch Praveen hands me to finish ("make PR N ready to merge", "fix up this branch"): that is a build ask, not a review turn, so "Not a checkpoint" does not apply. Its pushed commits stay as they are: my fixes land as new commits on top, and only those unpushed commits fold. The squash base is `git rev-parse origin/<branch>`, never a hash read from a listing (`gh` lists commits oldest first); prove it with `git merge-base --is-ancestor origin/<branch> HEAD` before reporting.

## What goes in
- **Only my files.** A branch carrying other tasks' staged or unstaged changes → explicit pathspec (`git commit --only <dir>/`), their work untouched. A pathspec commits whole files, so when `git diff <file>` shows a hunk that isn't mine, commit HEAD's blob plus only my hunks through a temp `GIT_INDEX_FILE`: `read-tree HEAD`, `update-index --cacheinfo` with that blob, `write-tree`, `commit-tree`, `update-ref` guarded on the old HEAD, then `git reset -q -- <paths>` so the real index matches the new HEAD (otherwise `git status` shows `MM` and the next plain commit from any session reverts the change). Simpler when the hunks are contiguous: `git apply --cached` a diff holding only my hunks, then a plain commit. Write that script in POSIX `sh` with paths and commit ids listed literally: zsh never word-splits an unquoted `$var`, so a list held in one variable arrives as one argument, `write-tree` yields an empty id and `update-ref` moves the branch. Abort on an empty id before `update-ref`. zsh-only syntax (`${(@f)…}`) also stops auto mode's safety check from parsing the script, so it waits for a manual approval. Shared wiring files (package.json, lockfile, routes) stay with their owner. A lockfile another session also changed hides its hunks inside mine: before committing one, read the staged diff's `version:` and `specifier:` lines and keep only the hunks my change explains.
- **Subject starts with the ticket key** when the work has one: `DPLK-212: feat(account): <summary>`, never a trailing `(DPLK-212)`, even where repo history mixes styles.
- **No attribution trailers in commits or PRs** — no `Co-Authored-By`, "Generated with" or tool footer; a teammate's `@additiv.com` co-author is fine. Never copy trailers from `git log`. Enforced by `hooks/block-dangerous-git.sh` and `hooks/commit-trailer-check.sh`.

## Squash: one commit per piece
- **A piece is the feature, not the plan.** Every fix, review fold or test on unpushed work of mine, and every follow-up plan or copy change on an unpushed feature, folds into that piece's commit, never stacks on top. A plan doc and its build are one piece: each plan revision, step checkpoint and chunk folds into the commit that added the plan, including the shipping commit that deletes it. A harness plan sits in gitignored `~/.claude/plans/`, so its first step's commit stands in for the plan's commit. Only work outside the feature (shared core, auth) gets its own commit. Rewrite the message to describe the work as it now stands. Unpushed history only.
- **Fold shapes:**
    - My commit is HEAD: read HEAD in the same command as the amend (`git log -1 --format=%s | grep -q '<subject>' && git commit --amend --only <paths> …`); a HEAD read earlier in the turn is stale, since a concurrent session's commit can land in between.
    - My commit sits below HEAD, only mine above it, clean tree: `git reset --soft <parent of my commit>`, recommit, `git diff --quiet <new> <old>`.
    - Another session's unpushed commits sit on top or in the range: rewriting them to fold is allowed when none of their work is lost. Keep each of their changes (its own commit, or folded into the piece it belongs to), and prove the tree unchanged with `git diff --quiet <new> <old>` before reporting. Only a guard denying the rewrite justifies a commit on top, its subject naming what it revises.

## Landing a branch
- **A child branch lands as one `git merge --squash` commit** authored by its main author; never `--no-ff`, never a fast-forward of its commits. A branch carrying several finished pieces still lands as one commit; one-commit-per-piece governs the branch's own history, not the landing.
- **Only on Praveen's typed "merge" / "land".** A shipping commit, a planner's ship GO or a question like "did you merge?" leaves it on the branch. "Merge into <branch>" means the local branch, and I land it myself.

## Undo
- **"Undo the commit of X" takes only X out of the commit.** Every other file stays committed and X's edits stay in the working tree (`git reset HEAD~1 -- X`, then amend). File content changes only when the ask names a revert ("revert", "drop the change", "restore the file"). "But not the edits" scopes what stays, never adds an action.

## Push and PR need a yes
- **`git push` is hook-denied** except to the harness backup remote (`PUSH_WHITELIST` in `hooks/block-dangerous-git.sh`). There Praveen's "push" runs as plain `git -C ~/.claude push origin master`; a denial of another shape is my command shape, not Praveen's rule, so the plain form is retried. `gh pr create` hook-asked.
- **Never offer a push as the next step.** Where a hook says to push, push in that turn; a summary never lists a push as pending. Status, "what now" and done replies included: local-only state is reported as a fact ("develop is 3 commits ahead of origin"), never as an action for Praveen, a push order or a warning about what happens before a push.

## Worktrees
- **"Work in a worktree" moves the session, not just the work:** create it, then `EnterWorktree` with its `path`. Carrying commits or files across while the session stays in the shared checkout is not it.
- **Inside a worktree session, plain git from the worktree cwd, one command per call, no chain.** Claude Code refuses git it can't prove stays inside the worktree: `cd` to the shared checkout, `git -C`, loops, subshells, `time -p`, or runtime variables around git.
- **Entering a worktree locks every running subagent to it,** blocking one that writes the shared checkout mid-step. Let it finish before `EnterWorktree`, then move its output with `cp` (test a suspected hook block before rewriting files by hand).
- **A `tsc` / vitest spike enumerating a plan's call sites** runs in a scratch worktree and commits to its own branch there; once that commit exists the worktree is removed, and the plan cites only the commit and branch, with the build in the main checkout.
- **An Agent with `isolation: worktree` started from `origin/<branch>`, not local HEAD** (seen 2026-11-09). With unpushed commits on the local branch, its output sits on a stale base, and cherry-picking its lockfile fights the newer one. When the local branch is ahead of origin, create the worktree yourself (`git worktree add -b <branch> <path> <local branch>`) and give the agent that path.
