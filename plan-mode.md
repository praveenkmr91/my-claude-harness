PLAN MODE RULES (hook-injected on EnterPlanMode or the first plan-file Write/Edit; owner of these rules, pointer in CLAUDE.md):
- **No unprompted ExitPlanMode.** A question gets an answer, nothing more; answers to plan questions are not approval to build. Raise ExitPlanMode only on an explicit "show the plan / proceed / approve" of that plan, given after the plan was presented; "back to work", "commit", answers to open items, "review/refine plan", and a build instruction issued before the plan existed ("plan X and implement it") are not approval. Approval covers the plan file only: dispatch an implementation step, in or out of plan mode, only on a later explicit "implement / build / start", never on "approved" alone. This overrides any harness nudge to end planning turns with approval.
- **Pre-mortem before the consult.** Assume the plan shipped and failed: 3-5 "failed because <specific cause in this plan>" headlines tied to named steps (never "requirements unclear"), plus the unstated load-bearing assumptions (file/API exists as described, prior step output correct, no files beyond those listed, convention still holds). High likelihood × high impact → a mitigation step or a raised finding; the rest → `→ verify:` checks on the step they threaten.
- **Cold read before the consult.** A reviewer sharing my transcript fills the plan's gaps from memory, so one reviewer sees only the file: a fresh `Plan` agent (never `fork`, never a resumed agent; model omitted, so it runs Opus), repo access on. The dispatch prompt is exactly this brief plus the plan path — add nothing, or the read is no longer cold: "Read <path>. You will execute this plan with only this file and the repo; you have no other context. Report, ranked by risk of a wrong build: every point where you would have to guess; every repo claim that is false (paths, symbols, cited `path:line`); every `→ verify:` that would pass on a broken step; every criterion no step delivers. Do not redesign." It tests the pre-mortem's assumption list against reality. Each finding is folded into the file — missing context gets written into the plan, since the implementer also gets only the file — or rejected with a one-line reason. Presenting the plan states: cold read N found, M folded, K rejected + reasons.
- **One Fable consult on the drafted plan.** Runs after the cold-read fold, so it also audits my rejections. Before showing it, one advisor pass (settings `advisorModel`) for gaps, wrong layer, missed sibling, lifecycle holes (refresh / remount / double-fire); fold findings in, then present with the same found / folded / rejected count. Advisor unavailable → one Fable fallback `Plan` agent (distinct from the cold read), `model: "fable"`, `[tier-override: plan review]`. Never a loop, never co-authoring.
- **Trivial plan → skip pre-mortem, cold read and consult.**
- **Size cap → split into chunks.** A plan over 4 steps, or over 15 files carrying a designed change (a mechanical rename or import sweep that `tsc` enumerates does not count), splits into chunks that each ship green on their own: own verify, own commit, own approval. Only the first chunk is detailed and reviewed; later chunks stay a draft and are re-verified against the tree after the previous chunk lands. A change that cannot go below the cap (an atomic dependency flip) ships as one chunk, with its call sites and spec expectations taken from a `tsc` / vitest spike. The spike runs in a scratch worktree and commits to its own branch there; once that commit exists the worktree is removed, and the chunk's plan and handoff cite only the commit and branch and state that the build runs in the main checkout. Transient state (a lock, a port holder, a branch tip) is re-read right before a plan or reply cites it. Reviews scale with size: a plan too big for one review pass is too big.
- **Approved plan = the file, not the context.** Draft at `~/.claude/plans/<slug>.md`. Repo work: on approval move it to `docs/plans/<slug>.md`, name the path in one line, implementation runs from it; the shipping commit deletes it. Harness / global-config work (`~/.claude/`): the plan stays in `~/.claude/plans/`, nothing lands in a repo.
- **Implementing a plan carries the gates, whether a handoff prompt sends it to another session or I orchestrate the slices myself.** Once the build is started, it goes to `implementer`, one step per dispatch, before the first source Write; the main thread writes a step itself only when it still carries an unsettled design call, and names that call in the reply. Per step: review + hook-joined lenses, harden on auth/token/money steps, step verify + lint + tsc + named live check, local commit. Before the final step: battery + harden + trim over the full range. Final: verify (runtime replay; advisor when the plan is irreversible or architectural) before the shipping commit.
- **Patterns to mirror.** For naming, error handling and tests, cite the sibling `path:line` the plan copies; none found → say so, never invent one.
- **Every step carries its own check** (`→ verify: <command or observation>`); a step with no check is not a step.
- **Acceptance criteria trace to steps.** A non-trivial plan opens with criteria `A1`, `A2`…, the ticket's worked example first; each step names the criteria it serves. A criterion no step serves is a gap — add the step or raise it, never ship around it.
- **Plan drift mid-implementation → edit the file, never just the chat.**
- **Plan = current instructions, never a journal.** Rewrite in place; superseded text is deleted. Decisions stay as present-tense constraints (one-line why if a future session would re-propose the alternative), without dates, attribution, revision notes, or ✅/status ticks. Progress lives in chat and commits. `hooks/plan-lint.js` refuses a plan edit that carries research narrative (journal words, prose paragraphs over 200 characters, a step without `→ verify:`, an Open item over 3 lines), in any repo's `plans/` directory and in `~/.claude/plans/`.
