# Plan mode

*Hook-injected on EnterPlanMode or the first plan-file Write/Edit; owner of these rules, pointer in CLAUDE.md.*

## Draft
- **The plan is the file.** Draft at `~/.claude/plans/<slug>.md`; harness work (`~/.claude/`) stays there and is deleted once its last step commits (`hooks/step-gate.sh` reads a plan file still on disk as a build in progress). Repo work moves to `docs/plans/<slug>.md` on approval, named in one line; the build runs from it and the shipping commit deletes it. An ask to implement or hand off implies approval, so the move lands in its own `docs(plans):` commit before the first build step or handoff prompt, never deferred to a chunk's commit. The implementer gets only the file, so every piece of context it needs is written into it. Plan drift mid-build → edit the file, never just the chat.
- **Tier.** Plan gates scale with the plan: names match `review-routing.md` (Trivial / Small / Big), size bounded by the chunk rule below.
    - Trivial: no plan required by `CLAUDE.md` but written anyway, verify lines only lint, type check, tests → no plan gate.
    - Small: a plan `CLAUDE.md` requires, within the chunk rule's bounds, no new mechanism → dry run and the advisor consult.
    - Big: a new mechanism (hook, rule doc, agent file, dep, layer, boundary, async state table), a plan the chunk rule splits, shared state, public API, money path → every gate in Draft and in Review (`plan-build.md`).
    - Plan tiers set plan gates only; handing the build to another session changes no tier.
- **Current instructions, never a journal.** Rewrite in place; superseded text is deleted. Decisions stay as present-tense constraints (one-line why if a future session would re-propose the alternative), without dates, attribution, revision notes or status ticks. Progress lives in chat and commits. Samples, traces and comparisons live in `plans/<name>.research.md` beside the plan; the plan cites them in one-line fact rows.
    - `hooks/plan-lint.js` refuses a plan edit in any `plans/` directory that carries: journal words (P1), prose over 200 characters (P2), a step without `→ verify:` (P3), an Open item over 3 lines (P4), a heading naming sampled / traced / log / notes / vs or a date (P5), a date elsewhere in the body (P6) unless it sits in backticks, quotes, a fence or a Source column, a criterion no step names (P7), a criteria or step section where nothing parses (P8), or a `(draft)` chunk carrying a line cite or `→ verify:` (P9). The `.research.md` file is exempt.
- **Criteria → steps → checks.** A Small or Big plan opens with criteria `A1`, `A2`… (one capital letter plus a number; the ticket's worked example first); each step names the criteria it serves and carries `→ verify: <command or observation>`. A criterion no step serves is a gap: add the step or raise it, never ship around it. For naming, error handling and tests, cite the sibling the plan copies (its symbol, or `path:line` for an unnamed line); none found → say so, never invent one.
- **Plan form: states and behaviour, not code.** A step gating UI on 2+ async inputs carries a state table: one row per input combination, columns for what renders and the gate. Plans fix behaviour, contracts and files; expression-level code (declaration order, import lines, local names) is the implementer's, checked by `tsc`.
- **Every borrowed mechanism names the problem it solves at its source, and that problem here.** A reference app's piece (a search, a read-before-write, a package, a fallback branch) enters a plan only with one line: why the source needs it (the code around it or its git log), and the state in this flow that hits the same problem. No such state → cut, never carried "to mirror". Code-time twin: `code-craft.md` "Right-size inherited/sibling boilerplate".
- **Dry-run before presenting (Small and Big); paper simulation is not enough.**
    - `dry-runner` executes every `→ verify:`, cited symbol or `path:line` and symbol census on the current tree; the dispatcher judges the output and writes the plan, so a check that cannot pass, or passes vacuously, surfaces before review. The dry run is folded before the cold read is dispatched, never in parallel: cold reads are capped at two rounds and dry runs are not, so a cold read spent on unrun checks is a round lost. Cost: about two minutes of wall-clock per round.
    - The tree is simulated after each step in order: a deleted or moved file or changed signature gets a census of every importer and caller, specs included, grepped by bare symbol (`\bcontactQuery\b`), never a call shape; install state counts (a workspace package links only into packages whose `package.json` declares it, so the creating step declares every consumer and runs one install); a step that breaks a file a later step fixes merges with it or reorders, and any reorder re-runs the simulation.
    - Every "what the code or frame does today" claim cites what was read for each caller or width it covers: the symbol (function, test name, export) where it is unique, a `file:line` only for an unnamed line, or the Figma node. A line number written from memory is often off by a few lines, and each fix re-triggers the dry run `hooks/done-claim-gate.sh` requires after the plan's last edit. Generalised from some callers is false until the rest are read. A worker's lead counts only after its whole region is read, and a spec asserting the behaviour is searched for before it is called a bug.
    - A revision is a new plan: a trim, merge or rewrite re-runs all of this on every step it adds or rewords, and re-reads every cited line after a compaction, since summary line numbers are stale. A fold that changes no `→ verify:` line, cited symbol or step order is not a revision: it re-runs nothing and takes the `plan gate: skip — <reason>` line, with the builder's pre-build dry run as the backstop for a fold misjudged as wording. The test covers every edit since the last review run, not only the latest, and switching between parallel and sequential execution is a step-order change.
- **Size cap → chunks.** Over 4 steps, or over 15 files carrying a designed change (a mechanical sweep `tsc` enumerates does not count), splits into chunks that each ship green alone: own verify and own approval, each folded into the plan's commit (`committing.md`). Only the first chunk is detailed and reviewed; later chunks stay a draft (a `(draft)` heading, criteria and files, no line cites or verify lines), detailed and verified once the previous chunk lands. A change that cannot go below the cap (an atomic dependency flip) ships as one chunk, its call sites and spec expectations taken from a `tsc` / vitest spike (`committing.md` owns where the spike runs and what the plan cites). A plan too big for one review pass is too big.

Review, approval and build rules: `~/.claude/plan-build.md`, injected with this file.
