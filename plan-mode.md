# Plan mode

*Hook-injected on EnterPlanMode or the first plan-file Write/Edit; owner of these rules, pointer in CLAUDE.md.*

## Draft
- **The plan is the file.** Draft at `~/.claude/plans/<slug>.md`; harness work (`~/.claude/`) stays there and is deleted once its last step commits (`hooks/step-gate.sh` reads a plan file still on disk as a build in progress). Repo work moves to `docs/plans/<slug>.md` on approval, named in one line; the build runs from it and the shipping commit deletes it. An ask to implement or hand off implies approval, so the move lands in its own `docs(plans):` commit before the first build step or handoff prompt, never deferred to a chunk's commit. The implementer gets only the file, so every piece of context it needs is written into it: decisions, contracts, files and siblings. What a failing test or `tsc` would settle is not context. Plan drift mid-build → edit the file, never just the chat.
- **Tier.** Plan gates scale with the plan: names match `review-routing.md` (Trivial / Small / Big), size bounded by the chunk rule below.
    - Trivial: no plan required by `CLAUDE.md` but written anyway, verify lines only lint, type check, tests → no plan gate.
    - Small: a plan `CLAUDE.md` requires, within the chunk rule's bounds, no new mechanism → dry run and the advisor consult.
    - Big: a new mechanism (hook, rule doc, agent file, dep, layer, boundary, async state table), a plan the chunk rule splits, shared state, public API, money path → every gate in Draft and in Review (`plan-build.md`).
    - Plan tiers set plan gates only; handing the build to another session changes no tier. A fold that adds a mechanism re-reads the tier.
- **Current instructions, never a journal.** Rewrite in place; superseded text is deleted. Decisions stay as present-tense constraints, without a why, dates, attribution, revision notes or status ticks. Progress lives in chat and commits. Evidence lives in `plans/<name>.research.md`, which the plan names once: facts, code reads, samples, traces, comparisons, rejected alternatives and each decision's why.
    - `hooks/plan-lint.js` refuses a plan edit in any `plans/` directory that carries: journal words (P1), prose over 200 characters (P2), a step without `→ verify:` (P3), an Open item over 3 lines (P4), a heading naming sampled / traced / log / notes / vs or a date (P5), a date elsewhere in the body (P6) unless it sits in backticks, quotes, a fence or a Source column, a criterion no step names (P7), a criteria or step section where nothing parses (P8), a `(draft)` chunk carrying a line cite or `→ verify:` (P9), a `Facts` or `Blocked on` heading or a `Rejected:` line (P10), or a second detailed chunk (P11). The `.research.md` file is exempt.
- **Criteria → steps → checks.** A Small or Big plan opens with criteria `A1`, `A2`… (one capital letter plus a number; the ticket's worked example first); each step names the criteria it serves and carries `→ verify: <command or observation>`. Each criterion names its source, the ticket's words or Praveen's typed ask; one I derived is marked `(derived)` and is his to accept or cut when the plan is presented, and a criterion added after that, by me or a reviewer, is a decision for Open, never a fold. A criterion no step serves is a gap: add the step or raise it, never ship around it. The Decided list is held to the same test from the other side: an entry that adds behaviour (a code path, fallback, state, guard or option) names the criterion that fails without it, and one that names none is not built: it moves to an `Upgrades, not built` list, one line each with what it buys and what it costs. A rejected approach and the read behind its cost go in the research file, where a dry run prints it. For naming, error handling and tests, cite the sibling the plan copies (its symbol, or `path:line` for an unnamed line); none found → say so, never invent one.
- **Plan form: states and behaviour, not code.** A step gating UI on 2+ async inputs carries a state table: one row per input combination, columns for what renders and the gate. Plans fix behaviour, contracts and files; expression-level code (declaration order, import lines, local names) is the implementer's, checked by `tsc`. Tests are named, not specified: one line per case; fixtures, helper options, record shapes, timestamps and quoting are the implementer's, checked by the test failing before the change (`harness.md` Maintenance owns which cases a hook test needs).
- **Every borrowed mechanism names the problem it solves at its source, and that problem here.** A reference app's piece (a search, a read-before-write, a package, a fallback branch) enters a plan only with one line: why the source needs it (the code around it or its git log), and the state in this flow that hits the same problem. No such state → cut, never carried "to mirror". Code-time twin: `code-craft.md` "Right-size inherited/sibling boilerplate".
- **Real-data assumptions get a spike before Steps are written.** A mechanism whose behaviour depends on data it does not control (session transcripts, API payloads, timing under the real runner) runs its core read or scan as throwaway code over the real corpus, one sample per falsifying axis (`CLAUDE.md` "Sample to falsify"), and tabulates its decisions per session (what it blocks, counts or skips); the rows that look wrong are read. The output lands in the research file; a comment in existing code is a claim, never a sample. For a hook the spike is the transcript replay in `harness.md` Maintenance. Read-only spike code lives in the session scratchpad (`implementer` writes it on a Fable thread); an assumption no spike can test is an Open risk, never a fact. A speed claim compares two layouts by alternating runs on the same machine in the same sitting; readings taken at different times are not comparable.
- **An unproven cause gets its probe shipped before the fix is planned.** When a plan's motive is a failure whose cause is a reading (intermittent, load-dependent, silent), the first change is the smallest one that makes the failure name its cause: one log line, one stderr message, one assertion message. It ships alone, and the fix is planned once a failing run has spoken. Seen 2026-11-14: a classifier rewrite was planned for most of a day on an unproven timeout, when a five-line stderr message in the stop gate would have confirmed it within the hour.
- **Dry-run before presenting (Small and Big); paper simulation is not enough.**
    - `dry-runner` executes every `→ verify:`, cited symbol or `path:line` and symbol census on the current tree; the dispatcher judges the output and writes the plan. Its prompt is the plan path, the step headings in scope, their research headings and the tree to read, nothing more: a fact worth checking is a cited claim in either, and a question about today's code is read, or sent to Explore, before the claim is written. The dry run is folded before the cold read is dispatched, never in parallel.
    - The tree is simulated after each step in order: a deleted or moved file or changed signature gets a census of every importer and caller, specs included, grepped by bare symbol (`\bcontactQuery\b`), never a call shape; install state counts (a workspace package links only into packages whose `package.json` declares it, so the creating step declares every consumer and runs one install); a step that breaks a file a later step fixes merges with it or reorders, and any reorder re-runs the simulation.
    - Every "what the code or frame does today" claim cites what was read for each caller or width it covers: the symbol (function, test name, export) where it is unique, a `file:line` only for an unnamed line, or the Figma node. Generalised from some callers is false until the rest are read. A worker's lead counts only after its whole region is read, and a spec asserting the behaviour is searched for before it is called a bug.
    - A revision re-runs this once per batch: a round's findings, or Praveen's answers, are all folded first, then one dry run names only the steps added or reworded since the last; cited lines are re-read after a compaction, since summary line numbers are stale. A fold that changes no `→ verify:` line, cited symbol or step order is not a revision: it re-runs nothing and takes the `plan gate: skip — <reason>` line. The test covers every edit since the last review run, not only the latest, and switching between parallel and sequential execution is a step-order change.
- **Size cap → chunks.** Over 4 steps, or over 15 files carrying a designed change (a mechanical sweep `tsc` enumerates does not count), splits into chunks that each ship green alone: own verify and own approval, each landing as its own commit (`committing.md`). Only the first chunk is detailed and reviewed; later chunks stay a draft (a `(draft)` heading, criteria and files, no line cites or verify lines), detailed and verified once the previous chunk lands. A change that cannot go below the cap (an atomic dependency flip) ships as one chunk, its call sites and spec expectations taken from a `tsc` / vitest spike (`committing-worktrees.md` owns where the spike runs and what the plan cites). A plan too big for one review pass is too big.

Review, approval and build rules: `~/.claude/plan-build.md`, injected with this file.
