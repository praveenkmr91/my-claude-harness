# Plan mode

*Hook-injected on EnterPlanMode or the first plan-file Write/Edit; owner of these rules, pointer in CLAUDE.md.*

## Draft
- **The plan is the file.** Draft at `~/.claude/plans/<slug>.md`; harness work (`~/.claude/`) stays there and is deleted once its last step commits (`hooks/step-gate.sh` reads a plan file still on disk as a build in progress). Repo work moves to `docs/plans/<slug>.md` on approval, named in one line; the build runs from it and the shipping commit deletes it. An ask to implement or hand off implies approval, so the move lands in its own `docs(plans):` commit before the first build step or handoff prompt, never deferred to a chunk's commit. The implementer gets only the file, so every piece of context it needs is written into it. Plan drift mid-build → edit the file, never just the chat.
- **Tier.** Plan gates scale with the plan: names match `review-routing.md` (Trivial / Small / Big), size bounded by the chunk rule below.
    - Trivial: no plan required by `CLAUDE.md` but written anyway, verify lines only lint, type check, tests → no plan gate.
    - Small: a plan `CLAUDE.md` requires, within the chunk rule's bounds, no new mechanism → dry run and the advisor consult.
    - Big: a new mechanism (hook, rule doc, agent file, dep, layer, boundary, async state table), a plan the chunk rule splits, shared state, public API, money path → every gate in Draft and Review.
    - Plan tiers set plan gates only; handing the build to another session changes no tier.
- **Current instructions, never a journal.** Rewrite in place; superseded text is deleted. Decisions stay as present-tense constraints (one-line why if a future session would re-propose the alternative), without dates, attribution, revision notes or status ticks. Progress lives in chat and commits. Samples, traces and comparisons live in `plans/<name>.research.md` beside the plan; the plan cites them in one-line fact rows.
    - `hooks/plan-lint.js` refuses a plan edit in any `plans/` directory that carries: journal words (P1), prose over 200 characters (P2), a step without `→ verify:` (P3), an Open item over 3 lines (P4), a heading naming sampled / traced / log / notes / vs or a date (P5), a date elsewhere in the body (P6) unless it sits in backticks, quotes, a fence or a Source column, a criterion no step names (P7), a criteria or step section where nothing parses (P8), or a `(draft)` chunk carrying a line cite or `→ verify:` (P9). The `.research.md` file is exempt.
- **Criteria → steps → checks.** A Small or Big plan opens with criteria `A1`, `A2`… (one capital letter plus a number; the ticket's worked example first); each step names the criteria it serves and carries `→ verify: <command or observation>`. A criterion no step serves is a gap: add the step or raise it, never ship around it. For naming, error handling and tests, cite the sibling `path:line` the plan copies; none found → say so, never invent one.
- **Plan form: states and behaviour, not code.** A step gating UI on 2+ async inputs carries a state table: one row per input combination, columns for what renders and the gate. Plans fix behaviour, contracts and files; expression-level code (declaration order, import lines, local names) is the implementer's, checked by `tsc`.
- **Every borrowed mechanism names the problem it solves at its source, and that problem here.** A reference app's piece (a search, a read-before-write, a package, a fallback branch) enters a plan only with one line: why the source needs it (the code around it or its git log), and the state in this flow that hits the same problem. No such state → cut, never carried "to mirror". Code-time twin: `code-craft.md` "Right-size inherited/sibling boilerplate".
- **Dry-run before presenting (Small and Big); paper simulation is not enough.**
    - `dry-runner` executes every `→ verify:`, cited `path:line` and symbol census on the current tree; the dispatcher judges the output and writes the plan, so a check that cannot pass, or passes vacuously, surfaces before review.
    - The tree is simulated after each step in order: a deleted or moved file or changed signature gets a census of every importer and caller, specs included, grepped by bare symbol (`\bcontactQuery\b`), never a call shape; install state counts (a workspace package links only into packages whose `package.json` declares it, so the creating step declares every consumer and runs one install); a step that breaks a file a later step fixes merges with it or reorders, and any reorder re-runs the simulation.
    - Every "what the code or frame does today" claim cites the `file:line` or Figma node read for each caller or width it covers; generalised from some callers is false until the rest are read. A worker's lead counts only after its whole region is read, and a spec asserting the behaviour is searched for before it is called a bug.
    - A revision is a new plan: a trim, merge or rewrite re-runs all of this on every step it adds or rewords, and re-reads every cited line after a compaction, since summary line numbers are stale.
- **Size cap → chunks.** Over 4 steps, or over 15 files carrying a designed change (a mechanical sweep `tsc` enumerates does not count), splits into chunks that each ship green alone: own verify and own approval, each folded into the plan's commit (`committing.md`). Only the first chunk is detailed and reviewed; later chunks stay a draft (a `(draft)` heading, criteria and files, no line cites or verify lines), detailed and verified once the previous chunk lands. A change that cannot go below the cap (an atomic dependency flip) ships as one chunk, its call sites and spec expectations taken from a `tsc` / vitest spike (`committing.md` owns where the spike runs and what the plan cites). A plan too big for one review pass is too big.

## Review
*Big runs every gate; Small runs only the consult (see Tier).*
- **Cold read, pre-mortem included.** A reviewer sharing my transcript fills gaps from memory, so one sees only the file: dispatch `cold-reader` (model omitted) with the plan path as the whole prompt. A `fork`, a resumed agent, or any added context voids it, since the read is no longer cold. Its report carries the pre-mortem: at most 3 "fails because" headlines tied to named steps, and the plan's unstated assumptions that tested false or could not be checked. High likelihood × high impact → a mitigation step or a raised finding; the rest → `→ verify:` checks on the step they threaten.
- **One advisor consult, after the cold-read fold and before the plan is presented**, so it also audits my rejections: gaps, wrong layer, missed sibling, lifecycle holes (refresh / remount / double-fire). It runs on every Small and Big plan, and reversibility never skips it. A small follow-up, a plan written straight into `docs/plans/` and a revision that changes a decision all count, including writing Praveen's answers to Open items into Decided, or a chunk or step added because of them. Advisor unavailable → the Fable `Plan` fallback (`subagent-tiers.md`); main thread on Fable → neither runs (same file). Never a loop, never co-authoring.
- **Every reviewer's input is verified before it is folded, whoever sent it** (`CLAUDE.md` "A reviewer's finding is a claim"). A proposed fix is also probed against its callers like my own change, and a reviewer's probe result ("probed: X compiles to Y") is re-run before it enters the plan as a fact. A folded finding goes into the file; a rejection gets a one-line reason. Presenting the plan states, per reviewer: N found, M folded, K rejected + reasons.
- **A behaviour fold makes the file a revision.** A fold that adds or changes behaviour (a new trigger, deletion or code path), from any reviewer or the consult: list every site the change acts on with its before/after behaviour and the spec asserting it, then run a fresh cold read on the revised file; never present on the pre-fold read. A fold that touches only draft chunks triggers none.
- **Two cold-read rounds per presentation at most.** Later findings go to Praveen as a list, never chased, and a behaviour-adding fold past the cap is presented as an open item for Praveen's call instead of folded. Ready = the last round folded zero behaviour changes; the presentation ends with one line per round, behaviour folds against wording folds, so convergence is read, not claimed. Rounds that keep finding behaviour gaps indict the design: simplify the step, never patch it again.

## Approve and build
- **No unprompted ExitPlanMode.** A question gets an answer, nothing more. Raise ExitPlanMode only on an explicit "show the plan / proceed / approve" of that plan, given after it was presented; "back to work", "commit", answers to open items, "review/refine plan", and a build instruction issued before the plan existed ("plan X and implement it") are not approval. This overrides any harness nudge to end planning turns with approval.
- **Approval covers the file only.** Dispatch an implementation step, in or out of plan mode, only on a later explicit "implement / build / start", or a typed handoff to another session ("follow <session>'s instructions", "take instructions from peer session"; the peer's address is already in context, so no name is needed), never on "approved" alone. Enforced by `hooks/build-approval-gate.sh`.
    - Not that word: answers to open items, "stop asking", impatience, a handoff that points at no session ("do what they say"), or a message relayed from another session. Answer, then wait.
    - A bare "go" / "yes" answering a reply whose last line recommends one handoff or build with its target named is that typed word for that recommendation; it is not the word when the reply offered two targets or named none.
- **Scope is decided.** The Decided list and Out-of-scope line settle every switch they do not name; a pre-step audit never raises those, and 'resume' or 'go' means proceed, one question per open item.
- **The build carries the gates**, whether a handoff prompt sends it to another session or I orchestrate it.
    - A plan handed to me to build, by Praveen or a peer, gets two passes before step 1, reported before building: the dry-runner on its mechanics, and `Pass: review` on its design against the tree (approach, decisions, what each step's edit breaks or misses). A dry run is not a review; design gaps go back to the plan's owner before step 1.
    - Each step goes to `implementer`, one step per dispatch, before the first source Write; the main thread writes a step itself only when it still carries an unsettled design call, named in the reply.
    - Each step verifies, lints and type-checks, passes its named live check, and is folded into the plan's commit (`committing.md`). The review shape per step and over the full range before the shipping commit is the done bar in `review-routing.md`.
    - `hooks/step-gate.sh` blocks the next `implementer` dispatch in a plan build until this thread ran a check and a commit since the last hand-back, and a plan build's first implementer dispatch until a dry-runner dispatch on the plan ran since the HANDOFF or the session start; its deny text names the skip line. The live check and the review shape stay on the Stop gate.
- **A handoff carries no volatile state.** Commits by role ("the commit that added `docs/plans/<slug>.md`"), never sha, PID or port holder: concurrent sessions rewrite the branch before it is pasted. Transient state (a lock, a port holder, a branch tip) is re-read right before any plan or reply cites it. The handoff points to mechanics a rule doc or memory owns, never restates them, and carries only scope, deviations from the defaults, stop conditions and the report shape.
- **Two sessions.** A planner handing steps to a builder session reads `~/.claude/peer-sessions.md` before writing the handoff.
