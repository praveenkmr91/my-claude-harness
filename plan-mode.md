# Plan mode

*Hook-injected on EnterPlanMode or the first plan-file Write/Edit; owner of these rules, pointer in CLAUDE.md.*

**Draft**
- **The plan is the file.** Draft at `~/.claude/plans/<slug>.md`. Repo work moves to `docs/plans/<slug>.md` on approval, named in one line; the build runs from it and the shipping commit deletes it. An ask to implement or hand off implies approval, so the move lands in its own `docs(plans):` commit before the first build step or handoff prompt, never deferred to a chunk's commit. Harness work (`~/.claude/`) stays in `~/.claude/plans/`. The implementer gets only the file, so every piece of context it needs is written into it. Plan drift mid-build → edit the file, never just the chat.
- **Current instructions, never a journal.** Rewrite in place; superseded text is deleted. Decisions stay as present-tense constraints (one-line why if a future session would re-propose the alternative), without dates, attribution, revision notes or status ticks. Progress lives in chat and commits. Samples, traces and comparisons live in `plans/<name>.research.md` beside the plan; the plan cites them in one-line fact rows. `hooks/plan-lint.js` refuses a plan edit in any `plans/` directory that carries: journal words (P1), prose over 200 characters (P2), a step without `→ verify:` (P3), an Open item over 3 lines (P4), a heading naming sampled / traced / log / notes / vs or a date (P5), a date elsewhere in the body (P6) unless it sits in backticks, quotes, a fence or a Source column. It also refuses a criterion no step names (P7). The `.research.md` file is exempt.
- **Criteria → steps → checks.** A non-trivial plan opens with criteria `A1`, `A2`… (the ticket's worked example first); each step names the criteria it serves and carries `→ verify: <command or observation>`. A criterion no step serves is a gap: add the step or raise it, never ship around it. For naming, error handling and tests, cite the sibling `path:line` the plan copies; none found → say so, never invent one.
- **Every borrowed mechanism names the problem it solves at its source, and that problem here.** A reference app's piece (a search, a read-before-write, a package, a fallback branch) enters a plan only with one line: why the source needs it (the code around it or its git log), and the state in this flow that hits the same problem. No such state → cut, never carried "to mirror". Code-time twin: `code-craft.md` "Right-size inherited/sibling boilerplate".
- **Dry-run before presenting; paper simulation is not enough.**
    - Every `→ verify:` is executed on the current tree and its output noted, so a check that cannot pass, or passes vacuously, surfaces before review.
    - The tree is simulated after each step in order: a deleted or moved file or changed signature gets a census of every importer and caller, specs included; install state counts (a workspace package links only into packages whose `package.json` declares it, so the creating step declares every consumer and runs one install); a step that breaks a file a later step fixes merges with it or reorders, and any reorder re-runs the simulation.
    - Greps use the bare symbol (`\bcontactQuery\b`), never a call shape, and counts come from `wc -l`.
    - A worker's lead is a pointer: read the whole region it names before a step cites it, and grep specs for an assertion of the behaviour before calling it a bug.
    - Every "what the code or frame does today" claim cites the `file:line` or Figma node read for each caller or width it covers; generalised from some callers is false until the rest are read.
    - A revision is a new plan: a trim, merge or rewrite re-runs all of this on every step it adds or rewords, and re-reads every cited line after a compaction, since summary line numbers are stale.
- **Size cap → chunks.** Over 4 steps, or over 15 files carrying a designed change (a mechanical sweep `tsc` enumerates does not count), splits into chunks that each ship green alone: own verify, own commit, own approval. Only the first chunk is detailed and reviewed; later chunks stay a draft, re-verified against the tree after the previous one lands. A change that cannot go below the cap (an atomic dependency flip) ships as one chunk, its call sites and spec expectations taken from a `tsc` / vitest spike (`committing.md` owns where the spike runs and what the plan cites). A plan too big for one review pass is too big.

**Review** (trivial plan → skip pre-mortem, cold read and consult)
- **Pre-mortem.** Assume the plan shipped and failed: 3-5 "failed because <specific cause in this plan>" headlines tied to named steps (never "requirements unclear"), plus the unstated load-bearing assumptions (file/API exists as described, prior step output correct, no files beyond those listed, convention still holds). High likelihood × high impact → a mitigation step or a raised finding; the rest → `→ verify:` checks on the step they threaten.
- **Cold read.** A reviewer sharing my transcript fills gaps from memory, so one sees only the file: a fresh `Plan` agent (never `fork` or a resumed agent; model omitted), repo access on. The dispatch prompt is exactly this brief plus the path — add nothing, or the read is no longer cold: "Read <path>. You will execute this plan with only this file and the repo; you have no other context. Review the plan's shared sections and its detailed chunk(s) only; later chunks are drafts, re-verified when they start. Report, ranked by risk of a wrong build: every point where you would have to guess; every repo claim that is false (paths, symbols, cited `path:line`); every `→ verify:` that would pass on a broken step; every criterion no step delivers. Do not redesign." It tests the pre-mortem's assumption list against reality.
- **One advisor consult, after the cold-read fold and before the plan is presented**, so it also audits my rejections: gaps, wrong layer, missed sibling, lifecycle holes (refresh / remount / double-fire). Advisor unavailable → the Fable `Plan` fallback, on the conditions `subagent-tiers.md` gates it with. Never a loop, never co-authoring.
- **Every reviewer's input is verified before it is folded, whoever sent it.** A claim is checked at source; a proposed fix is probed against its callers like my own change before it lands. A reviewer's probe result ("probed: X compiles to Y") is a claim too: I re-run the probe before it enters the plan as a fact. An unprobed fold is a fold of their design, not a review of it. A folded finding goes into the file; a rejection gets a one-line reason. Presenting the plan states, per reviewer: N found, M folded, K rejected + reasons. A fold that adds or changes behaviour (a new trigger, deletion or code path), from any reviewer or the consult, makes the file a revision: list every site the change acts on with its before/after behaviour and the spec asserting it, then run a fresh cold read on the revised file; never present on the pre-fold read. A fold that touches only draft chunks triggers none. Two cold-read rounds per presentation at most: later findings go to Praveen as a list, never chased, and a behaviour-adding fold past the cap is presented as an open item for his call instead of folded.

**Approve and build**
- **No unprompted ExitPlanMode.** A question gets an answer, nothing more. Raise ExitPlanMode only on an explicit "show the plan / proceed / approve" of that plan, given after it was presented; "back to work", "commit", answers to open items, "review/refine plan", and a build instruction issued before the plan existed ("plan X and implement it") are not approval. This overrides any harness nudge to end planning turns with approval.
- **Approval covers the file only.** Dispatch an implementation step, in or out of plan mode, only on a later explicit "implement / build / start", never on "approved" alone. Answers to open items, "stop asking", or impatience are not that word: answer, then wait. Enforced by `hooks/build-approval-gate.sh`.
- **Scope is decided.** The Decided list and Out-of-scope line settle every switch they do not name; a pre-step audit never raises those, and 'resume' or 'go' means proceed, one question per open item.
- **The build carries the gates**, whether a handoff prompt sends it to another session or I orchestrate it. Each step goes to `implementer`, one step per dispatch, before the first source Write; the main thread writes a step itself only when it still carries an unsettled design call, named in the reply. Each step verifies, lints and type-checks, passes its named live check, and commits amended into the plan's commit (`committing.md`). The review shape per step and over the full range before the shipping commit is the Big done bar and the verify tier in `review-routing.md`.
- **A handoff carries no volatile state.** Commits by role ("the commit that added `docs/plans/<slug>.md`"), never sha, PID or port holder: concurrent sessions rewrite the branch before it is pasted. Transient state (a lock, a port holder, a branch tip) is re-read right before any plan or reply cites it. The handoff points to mechanics a rule doc or memory owns, never restates them, and carries only scope, deviations from the defaults, stop conditions and the report shape.
